Question Link : https://leetcode.com/problems/lfu-cache/description/

* Core intuition:
  An LFU cache needs to answer two questions in O(1): which key has the lowest frequency, and among keys with the same frequency, which one was least recently used.

* keyMap:
  Maintain a map where key = cache key and value = its current frequency (number of accesses).

* freqMap:
  Maintain another map where key = frequency and value = an LRU cache containing all key-value pairs having that frequency.

* Why LRU inside each frequency:
  LFU first chooses the key with the lowest frequency. If multiple keys have the same frequency, the least recently used key must be evicted.

* minFreq:
  Track the smallest frequency currently present in the LFU cache so that the corresponding LRU cache can be found directly through freqMap.

* New key insertion:
  A new key starts with frequency 1, so it is inserted into the LRU cache corresponding to frequency 1.

* New key when cache is full:
  First find the LRU cache corresponding to minFreq, then remove its rear node because it is the least recently used key among all least-frequently-used keys.

* Existing key insertion:
  Updating an existing key counts as an access, so first find its current frequency using keyMap, remove it from that frequency's LRU cache, and insert it into the LRU cache whose frequency is one greater.

* get():
  If the key does not exist in keyMap, it is not present in the LFU cache, so return -1.

* get() for an existing key:
  Find its frequency from keyMap, find its LRU cache from freqMap, retrieve its value, remove it from the current LRU cache, and move it to the LRU cache corresponding to frequency + 1.

* Why a key moves to the head:
  Moving a key to the head of its new frequency's LRU cache marks it as the most recently used key at that frequency.

* LRU head:
  Most recently used key within that frequency.

* LRU rear:
  Least recently used key within that frequency and therefore the eviction candidate when that frequency is the minimum frequency.

* removeNode():
  First use keyMap to determine the key's frequency, then remove the key from the corresponding LRU cache.

* Empty frequency bucket:
  If an LRU cache becomes empty after removing its last key, remove that frequency from freqMap because it is no longer an active frequency.

* Updating minFreq:
  If the removed frequency was minFreq and its bucket became empty, minFreq must move to the next valid frequency. When a new key is inserted, minFreq becomes 1 because every new key starts with frequency 1.

* Why HashMap inside LRU:
  The HashMap maps key -> Node, allowing the node to be located in O(1) without traversing the linked list.

* Why doubly linked list inside LRU:
  Once a node is found through the HashMap, its previous and next pointers allow it to be removed or moved to the head in O(1).

* Why dummy nodes are not required in the LRU:
  The implementation explicitly handles head, rear, and single-node cases.

* Overall structure:
  keyMap answers "what is this key's frequency?", freqMap answers "which keys have this frequency?", and each LRU cache answers "which key at this frequency was used least recently?"

* Example:
  Suppose key 1 has frequency 2 and key 2 has frequency 3. keyMap stores 1 -> 2 and 2 -> 3, while freqMap stores 2 -> LRU containing key 1 and 3 -> LRU containing key 2.

* If key 3 is inserted while the cache is full and minFreq = 2, key 1 is considered before key 2 because frequency 2 is lower than frequency 3.

* If keys 1 and 4 both have frequency 2, their order inside freqMap.get(2) determines which one is evicted: the rear/least-recently-used key is removed.

* Time Complexity: O(1)

* Space Complexity: O(capacity)
