Question Link : https://leetcode.com/problems/rectangle-area-ii/description/

* Problem:
  Given multiple rectangles, compute the total area covered by them.
  Overlapping regions must be counted only once.

* Key difficulty:
  Rectangles can overlap in complex ways, so naively adding their areas causes double counting.

* Key geometric observation:
  Sweep across the X axis. For any x-interval [x1, x2], vertical coverage remains constant, so area = width * verticalCoverage.

* Sweep line concept:
  Imagine a vertical line moving from left -> right. Rectangles start or end at certain x-coordinates called EVENTS.

* Event representation:
  For rectangle [x1,y1,x2,y2]: x1 -> ADD [y1,y2], x2 -> REMOVE [y1,y2].

* Why this works:
  At x1 the rectangle starts contributing to the covered height, and at x2 it stops contributing.

* Event data structure:
  TreeMap<x, List<events>> is used because events must be processed in sorted x order.

* Active intervals:
  Maintain y-intervals of rectangles currently intersecting the sweep line.
  TreeMap<yInterval, frequency> acts as an ordered multiset.

* Why TreeMap instead of TreeSet?
  Multiple rectangles can have the same [y1,y2] interval, so maintain frequency: ADD -> frequency++, REMOVE -> frequency--. Remove the interval only when its frequency becomes 0.
  TreeMap also keeps intervals sorted by y1, allowing calcHeight() to merge overlapping intervals.

* Important invariant:
  activeRectangle always contains all rectangles intersecting the current sweep strip, with the correct frequency for duplicate y-intervals.

* Sweep algorithm:
  For each currX: area += (currX - prevX) * currentHeight; process ADD/REMOVE events; recalculate height; set prevX = currX.

* Why calculate area before processing events?
  [prevX, currX] corresponds to the rectangles that were active before reaching currX, so those events must only affect the next strip.

* Computing vertical coverage:
  Sort active intervals by y1 and merge overlapping intervals.
  Example: [1,5] and [3,8] have naive length 9, but their union is [1,8] with length 7.

* Interval merging:
  If nextStart > currentEnd, there is a gap, so add the current interval and start a new one; otherwise extend currentEnd.

* Why TreeMap is sufficient:
  Its ordering lets calcHeight() process active intervals from bottom -> top and calculate their union length.

* Area accumulation:
  For every consecutive pair of x-events: area += deltaX * unionOfActiveYIntervals.

* Time Complexity: Event generation and TreeMap operations take O(n log n), while calcHeight() scans active intervals at every event.
        
        O(n²)

* Space Complexity: 
        
        O(n).

* Why modulo?
  The total area can exceed the integer range, so the result is maintained modulo 1e9+7.
